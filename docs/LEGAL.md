# เอกสารนโยบายของ CUSA SSO

หน้า `/privacy` และ `/terms` เป็นหน้า React สาธารณะ เปิดโดยตรง รีเฟรช และอ่านได้โดยไม่ต้องล็อกอินหรือเชื่อมต่อฐานข้อมูล Frontend เลือกหน้าเอกสารก่อน mount `App` จึงไม่เรียก `/auth/me`, `/auth/status` หรือ Admin API บนหน้าเหล่านี้

ข้อมูลสมาคม ที่อยู่ โทรศัพท์ และอีเมลมาจากข้อมูลที่เจ้าของโครงการแจ้ง เก็บรวมที่ `web/src/models/legal.ts` ส่วนเนื้อหาและรูปแบบอยู่ใน `web/src/views/Legal.tsx` และ `legal.css` ไม่มีการอ่าน `.env` หรือส่ง secret ไปยังหน้าเอกสาร

## ขอบเขตเนื้อหา

- ความเป็นส่วนตัว: ผู้ควบคุม/ช่องทางติดต่อ ข้อมูลและแหล่งที่มา วัตถุประสงค์/ฐานกฎหมาย ความจำเป็น การแบ่งข้อมูลราย Service ผู้รับข้อมูล การโอนต่างประเทศ คุกกี้ อายุข้อมูล ความปลอดภัย สิทธิ/การใช้สิทธิ ผู้เยาว์ ข้อมูลอ่อนไหว เหตุละเมิด และการเปลี่ยนประกาศ
- ข้อกำหนด: ขอบเขต/การรับทราบ คุณสมบัติ บัญชี/MFA สิทธิ์ราย Service การใช้งานที่ห้าม ผู้เชื่อมต่อ API บุคคลภายนอก ความพร้อมใช้งาน การระงับ/ขอทบทวน ทรัพย์สินทางปัญญา ความรับผิด กฎหมายไทย/ข้อพิพาท การเปลี่ยนเงื่อนไข และช่องทางติดต่อ
- ทั้งสองหน้ามีสารบัญ anchor links, ลิงก์ข้ามเอกสาร, ชื่อแท็บเฉพาะ, ปุ่มพิมพ์/บันทึก PDF ผ่าน browser print และรูปแบบสำหรับมือถือ/พิมพ์
- ลิงก์จาก Login/MFA/Service login เปิดแท็บใหม่แบบ `noopener noreferrer` ไม่แนบ query ของ OAuth, `returnTo`, state, code หรือค่าลับไปใน URL เอกสาร

## สิ่งที่ต้องตรงกับการปฏิบัติงานจริง

เอกสารนี้เป็นร่างสำหรับใช้กับระบบที่พัฒนา ไม่ใช่ใบรับรองการปฏิบัติตามกฎหมาย ก่อนประกาศใช้งานจริง ผู้รับผิดชอบสมาคมควรให้ผู้เชี่ยวชาญกฎหมายไทยตรวจเนื้อหาและยืนยันการปฏิบัติงานที่รองรับ โดยเฉพาะประเด็นต่อไปนี้ ไม่ใช่การขออนุมัติก่อนพัฒนาหรือก่อนตรวจหน้าเว็บในเครื่อง

1. ยืนยันชื่อผู้ควบคุมข้อมูล/สถานะนิติบุคคล ขอบเขตความรับผิดของแต่ละ Service และอีเมลรับคำขอที่มีผู้ดูแลจริง ข้อมูลที่ได้รับยังไม่ได้ระบุการแต่งตั้ง DPO จึงไม่ระบุชื่อบุคคลหรืออ้างว่าแต่งตั้งแล้ว ต้องประเมินหน้าที่แต่งตั้งตามลักษณะกิจกรรมจริง
2. ระบุวันประกาศใช้และเก็บสำเนาของแต่ละ version; วันที่ปรับปรุงในหน้าเอกสารไม่ใช่หลักฐานว่าได้ประกาศใช้หรือผู้ใช้ทุกคนยอมรับแล้ว
3. จัดทำทะเบียนกิจกรรมและจับคู่ฐานกฎหมายให้ตรงกับความสัมพันธ์จริง ฐานสัญญาใช้เฉพาะเมื่อผู้ใช้เป็นคู่สัญญาและข้อมูลจำเป็นต่อสัญญา; ประเมินประโยชน์โดยชอบด้วยกฎหมายก่อนอาศัยฐานนั้น การอ่านนโยบายไม่ใช่ consent สำหรับทุกกิจกรรม
4. กำหนดตาราง retention ที่มีระยะเวลา ผู้รับผิดชอบ และวิธีลบ/ทำให้ไม่ระบุตัวบุคคล รวมบัญชี soft-delete, Audit Log, archive, backup, คำขอใช้สิทธิ และ legal hold ไม่ใช้ “90 วัน” กับข้อมูลทุกประเภทเพียงเพราะเคยเป็นตัวอย่างในเอกสารออกแบบ นโยบายแสดงอายุ credentials จริงและเกณฑ์ความจำเป็นของข้อมูลอื่น; ควรแทนเกณฑ์ด้วยระยะเวลาจริงเมื่อสมาคมกำหนดได้
5. `server/src/scripts/cleanup.ts` ลบเฉพาะข้อมูลชั่วคราวที่หมดอายุเมื่อผู้ดูแลเรียกใช้งาน ต้องตั้งรอบงานเอง ไม่มีการ purge ผู้ใช้หรือ Audit Log อัตโนมัติ การ revoke บัญชีไม่ใช่การทำคำขอลบตาม PDPA สำเร็จทั้งหมด ต้องมีขั้นตอนจำกัด/ลบข้อมูลโดยผู้มีสิทธิ์และรักษาหลักฐานที่มีกฎหมายรองรับตาม [คู่มือ Audit](AUDIT-OPERATIONS.md)
6. ตรวจผู้ให้บริการจริง ประเทศที่ประมวลผล/สำรองข้อมูล สัญญาผู้ประมวลผล และมาตรการโอนต่างประเทศตามมาตรา 28–29 และประกาศปัจจุบัน ไม่อ้างว่าใช้ Google/Upstash แล้วทำ DPA หรือมาตรการโอนครบแล้วโดยอัตโนมัติ หน้าเอกสารกล่าวถึง Upstash แบบมีเงื่อนไขเมื่อเปิดใช้งาน
7. จัดขั้นตอนรับและตรวจคำขอใช้สิทธิ การแจ้งผล การจำกัดการเปิดเผยข้อมูลผู้อื่น การติดตาม deadline และ incident response การมี `mailto:` ยังไม่ได้สร้าง ticket system หรือส่งแจ้งเหตุละเมิดให้อัตโนมัติ ระยะเวลา 30 วันในหน้านโยบายระบุเฉพาะคำขอเข้าถึง/สำเนาตามมาตรา 30 ไม่อ้างว่าทุกสิทธิมี deadline เดียวกัน
8. ประเมินสถานะผู้ให้บริการและหน้าที่เก็บข้อมูลจราจรตามกฎหมายคอมพิวเตอร์จากลักษณะบริการจริง Audit Log ของแอปไม่เท่ากับ traffic log ที่ครบทุกข้อกำหนดของกฎหมายโดยอัตโนมัติ

ไม่มีการเพิ่ม checkbox “ยินยอม PDPA” หรือบันทึก acceptance ปลอมจากการเปิดหน้า หากต้องมีหลักฐานการยอมรับข้อตกลงที่มี version ต้องออกแบบการรับทราบอย่างชัดเจนและบันทึกผู้ใช้/เวลา/ฉบับที่แสดงจริงในขั้นตอนที่เหมาะสม โดยแยกจาก consent ของกิจกรรมทางเลือก

## เอกสารกฎหมายที่ใช้ตรวจร่าง

ตรวจแหล่งทางการ ณ 29 กันยายน 2569 เนื้อหาเป็นข้อความร่างสำหรับบริการนี้ ไม่ใช่การคัดลอกประกาศขององค์กรอื่น

- [พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 — สำเนาราชกิจจานุเบกษาเผยแพร่โดยกรมประชาสัมพันธ์](https://law.prd.go.th/th/file/get/file/20231122b19b536a4647f29a6d99e228909779b4120136.PDF): มาตรา 19–26, 28–37, 40–42 และ 73 ตามประเด็นที่เกี่ยวข้อง
- [พ.ร.บ.ว่าด้วยธุรกรรมทางอิเล็กทรอนิกส์ พ.ศ. 2544 และฉบับแก้ไข — กระทรวง อว.](https://www.ops.go.th/th/plan-policy/thailand-policy-regulation/item/13621-Electronic-Transactions): การแสดงเจตนาและเอกสารอิเล็กทรอนิกส์ ไม่ถือว่า Google login พิสูจน์อำนาจแทนหรือความยินยอมได้ทุกกรณี
- [คำอธิบายกฎหมายธุรกรรมทางอิเล็กทรอนิกส์ — ETDA](https://www.etda.or.th/th/contact/faq/ETDA.aspx)
- [พ.ร.บ.ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ (ฉบับที่ 2) พ.ศ. 2560 — กระทรวงพาณิชย์](https://ictc.ops.moc.go.th/th/content/category/detail/id/142/iid/5890)
- [หลักเกณฑ์การเก็บรักษาข้อมูลจราจรทางคอมพิวเตอร์ พ.ศ. 2564 — สวทช.](https://pub.nstda.or.th/gov-dx/computer-traffic-information/)

กฎหมายและประกาศอาจเปลี่ยนได้ ต้องทบทวนเมื่อเปลี่ยนการเก็บข้อมูล ผู้ให้บริการ หรือรูปแบบบริการ ไม่อ้าง certification, “ปลอดภัย 100%” หรือการสอดคล้องกฎหมายครบทุกด้านจากการเพิ่มหน้าเอกสารเพียงอย่างเดียว
